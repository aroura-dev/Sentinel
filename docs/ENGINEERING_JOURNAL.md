# Sentinel 技术思考日志

> 这不是开发流水账，也不记录“今天改了什么”。这里只记录关键技术问题、方案取舍、验证方式和仍存在的边界。

## 记录格式

每个议题尽量回答六个问题：

1. **问题**：系统遇到了什么真实约束？
2. **备选**：考虑过哪些实现？
3. **决策**：最终选择什么，为什么？
4. **取舍**：方案牺牲了什么？
5. **验证**：如何证明决策有效？
6. **遗留**：哪些问题没有被当前方案解决？

## 1. 从消息发送到异常闭环

**问题**

单纯“把消息发出去”不能解决物流异常处置。异常需要被发现、建单、通知、跟踪、关闭，并保留可审计证据。

**备选**

- 只做消息发送平台。
- 只做工单系统，消息渠道接入第三方平台。
- 把异常发现、工单、通知和 AI 决策放在一个业务服务里。

**决策**

以物流异常为业务主线：状态机负责节点流转，工单负责责任闭环，通知负责触达，Agent 负责诊断和文案，LiteFlow 负责编排。

**取舍**

系统边界变大，本地依赖增多；换来的是完整业务链路，而不是只有技术组件的演示。

**验证**

主链路可以从订单轨迹一直追到通知状态和 Agent 调用日志。

**遗留**

当前聚焦单组织内的自动闭环，跨组织的复杂工单权限和 SLA 仍未覆盖。

## 2. 状态机与并发状态更新

**问题**

物流节点更新可能来自定时任务、接口回调或人工操作。如果只做普通 `update status`，并发请求可能发生状态覆盖。

**备选**

- 只依赖数据库行锁。
- 每次更新直接覆盖状态。
- 用状态机定义合法迁移，再使用乐观锁处理冲突。

**决策**

状态机负责“能不能流转”，乐观锁负责“并发时谁成功”。非法状态在进入数据库前就被拒绝。

**取舍**

新增节点时必须同步维护迁移规则，代码比任意状态赋值更严格。

**验证**

节点迁移和状态权限有单元测试覆盖，冲突更新不会静默覆盖。

**遗留**

生产级高并发场景仍需要结合重试策略、幂等请求号和业务审计进一步压测。

## 3. Outbox：业务事务与消息事件一致

**问题**

如果先写数据库、再发送 Kafka，可能出现“数据库成功但消息丢失”；如果先发消息、再写数据库，又可能出现“消息已发但业务回滚”。

**备选**

- 本地事务后直接发送消息。
- 引入分布式事务。
- 业务表和 Outbox 事件同事务落库，由后台任务投递。

**决策**

使用 Outbox：业务写操作和事件记录在同一 MySQL 事务中提交，后台 Dispatcher 轮询并投递；消费端使用唯一键幂等消费。

**取舍**

引入最终一致性和轮询成本，需要处理重复投递。

**验证**

事件唯一键、Dispatcher 和幂等消费均有测试；Outbox 扫描使用 `status + next_retry_at + id` 复合索引。

**遗留**

当前实现适用于本地和中小规模场景，尚未验证多实例租约锁和超大规模积压。

## 4. Redis 滑动窗口去重

**问题**

固定时间窗口容易在窗口边界误判。例如同一消息在 59 秒和 61 秒到达，固定桶可能无法正确识别。

**备选**

- 只使用固定 TTL key。
- 只用 MySQL 唯一键。
- Redis ZSet 保存时间戳，Lua 原子完成清理、计数和写入，再由 MySQL 唯一键兜底。

**决策**

Redis 负责高性能窗口判断，Lua 保证多命令原子性，MySQL 唯一键负责最终一致性兜底。

**取舍**

Redis 与 MySQL 承担不同职责，逻辑更复杂；但去重延迟和误判率更可控。

**验证**

模拟窗口边界、重复消息和并发请求，验证首次放行、窗口内拦截。

**遗留**

跨地域多活和 Redis 故障恢复场景仍需进一步设计。

## 5. Kafka、消费者组与线程池隔离

**问题**

短信、邮件、推送和不同业务消息如果在同一消费者或同一线程池处理，慢渠道会阻塞其他消息。

**备选**

- 单个消费者组统一处理。
- 每个请求创建一个线程。
- 按业务、撤回、轨迹拆分消费者组，再按渠道和消息类型隔离线程池。

**决策**

不同消息类型使用独立 topic/consumer group；每个下游任务使用独立动态线程池，队列容量 128，达到上限后由 CallerRunsPolicy 产生背压。

**取舍**

线程池和消费者数量增加，配置和观测成本更高。

**验证**

本地压测观察 consumer lag、QPS、P95/P99 和最终通知状态。

**遗留**

当前数据来自本地单机，不能直接推广为生产容量结论。

## 6. AI Agent 的边界与降级

**问题**

模型调用可能超时、返回格式错误，或者给出未经审批的业务写操作建议。通知链路不能因为模型故障整体失败。

**备选**

- 让模型直接执行所有业务操作。
- 模型失败后无限重试。
- 模型只作为能力节点，写操作审批，失败时确定性降级。

**决策**

只读工具允许自动执行；赔付、状态流转等写操作保留审批。模型异常时回退模板或转人工，并记录 `degraded` 状态。

**取舍**

失去一部分“全自动”体验，换来可控性和可审计性。

**验证**

模拟模型超时、格式错误和服务停机，确认通知仍可完成。

**遗留**

模型质量、成本和真实业务准确率需要在更大数据集上评估。

## 7. 微服务拆分边界

**问题**

微服务可以体现独立部署和异步解耦，但拆分过细会引入跨服务事务、链路追踪、接口契约和本地调试成本。

**备选**

- 按技术层拆分成 controller / service / dao。
- 按业务域拆分成鉴权、物流、消息、Agent。
- 继续保留单个业务进程，只在逻辑上分模块。

**决策**

按业务域拆分为 `auth-service`、`logistics-service`、`msg-service`、`agent-service`，Gateway 统一入口；每个服务拥有独立数据库，服务间通过 REST 和 Kafka 通信。

**取舍**

放弃跨服务本地事务，改为 Outbox、幂等消费和 `traceId` 关联；换来域边界清晰、部署独立和故障隔离。

**验证**

通过 Gateway 登录、触发物流通知，验证 Agent、Logistics、Msg 三个库的回写和最终状态。

**遗留**

服务契约、版本兼容和发布治理仍需继续完善，当前重点是业务闭环可验证，而不是追求服务数量。
## 8. traceId 与可观测性

**问题**

异常处置跨越订单、工单、通知和 Agent，如果没有统一关联标识，无法回答“这条异常为什么这样处理”。

**备选**

- 每个模块独立记录日志。
- 只记录最终状态。
- 使用 traceId 贯穿业务和 Agent 调用。

**决策**

订单、工单、通知和 `agent_call_log` 共享 traceId；记录 token、工具、耗时、状态和降级原因。

**取舍**

日志字段和存储成本增加，但问题定位可以从人工推断转为基于调用记录回放。

**验证**

可以通过 traceId 还原一次异常从识别到通知完成的处理过程。

**遗留**

当前以日志和调用表为主，尚未接入完整分布式追踪平台。

## 9. SQL 索引与基准

**问题**

Outbox 任务表持续增长后，高频扫描 `status + next_retry_at` 容易变成全表扫描和 filesort。

**备选**

- 增加定时清理。
- 分页扫描但没有合适索引。
- 建立与查询顺序一致的覆盖索引。

**决策**

使用 `status + next_retry_at + id` 复合索引，让过滤和排序都命中索引。

**取舍**

索引增加写放大和存储成本，需要控制索引数量。

**验证**

20 万行本地基准中，扫描估算从约 199408 行降到约 200 行，中位耗时约 1.4ms。

**遗留**

这是隔离基准，不代表真实生产收益；仍需结合写入比例和表增长持续观察。

## 10. 本地可复现与 CI 验收

**问题**

如果项目缺少可执行的启动与验证路径，源码本身无法证明配置、初始化脚本和端口可用；如果 CI 只编译不启动，也无法发现部署问题。

**备选**

- 只提供源码和运行说明。
- 只做单元测试。
- Docker Compose 启动完整链路，CI 增加 smoke 验收。

**决策**

本地使用 `infra/tools/up.sh` 启动四个 MySQL、Redis、Kafka 和业务服务；CI 覆盖微服务测试、Compose 和 smoke 验收。

**取舍**

CI 时间更长，镜像构建需要网络和磁盘资源。

**验证**

健康检查 `UP`、管理员登录成功、前端经 Nginx 代理访问后端成功。

**遗留**

GitHub Hosted Runner 无法覆盖真实模型调用、真实短信和长时稳定性。

## 技术结论

Sentinel 的工程重点是围绕以下问题建立可验证的闭环：

> **状态是否合法 → 并发是否覆盖 → 事务是否丢事件 → 消费是否重复 → 慢链路是否阻塞 → 模型失败是否降级 → 全链路是否可追踪。**
